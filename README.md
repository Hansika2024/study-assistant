# Study Assistant

An AI-powered study assistant that turns free-form text (a topic, or pasted notes) into an interactive **quiz** or a **flashcard deck**, generated by the Gemini API and validated end-to-end before it ever reaches the UI.

## Tech stack

- **Frontend:** React + Vite
- **Backend:** Node.js + Express
- **AI:** Gemini API (`@google/genai`)
- **Validation:** Zod (schema) + custom logical validation

## Architecture

```
USER
  │
  ▼
React Frontend (PromptInput, ModeSelector, GenerateButton)
  │
  ▼
useStudyGenerator() hook  ──►  api.js  ──►  POST /api/generate
                                                  │
                                                  ▼
                                     Express backend
                                       │
                                       ├─ request validation
                                       ├─ prompt construction
                                       ├─ Gemini call (timeout + single retry)
                                       ├─ JSON parsing
                                       ├─ Zod schema validation
                                       └─ logical validation
                                                  │
                                                  ▼
                                          Gemini API
                                                  │
                                                  ▼
                                   Validated StudyResult (JSON)
                                                  │
                                                  ▼
                                     React frontend re-validates
                                                  │
                                                  ▼
                                           ResultView
                                          /          \
                                       Quiz       Flashcards
                                         │              │
                                       Score        Progress
                                         │              │
                                    Wrong answers   Missed cards
                                         └──────┬───────┘
                                          Retry / Review
```

The backend exists purely to keep the Gemini API key server-side and to be the single point where AI output is validated before it can reach the UI — the frontend never talks to Gemini directly.

## Setup

1. Clone the repo and create `.env` at the **repo root** (same level as `frontend/` and `server/`), based on `.env.example`:

   ```
   GEMINI_API_KEY=your_gemini_api_key_here
   ```

2. Install dependencies in both folders:

   ```bash
   cd server && npm install
   cd ../frontend && npm install
   ```

3. Run the backend (from `server/`):

   ```bash
   npm run dev
   ```

   > Note: this uses `nodemon`, which by default does **not** watch `.env` for changes. If you edit your API key, fully stop (`Ctrl+C`) and restart the process — saving the file alone will not reload it.

4. Run the frontend (from `frontend/`):

   ```bash
   npm run dev
   ```

5. Health check: `GET http://localhost:5000/api/health` should return `{ "success": true, "message": "Study Assistant backend is running" }`.

## API contract

**`POST /api/generate`**

Request:

```json
{
  "input": "Explain binary search and its time complexity",
  "mode": "quiz"
}
```

Success response:

```json
{
  "success": true,
  "data": {
    "type": "quiz",
    "title": "Binary Search",
    "questions": [ /* 5–10 items */ ]
  }
}
```

Error response (always this shape):

```json
{
  "success": false,
  "error": {
    "code": "INVALID_AI_RESPONSE",
    "message": "We couldn't generate a valid study set. Please try again."
  }
}
```

| Situation | Code | HTTP status |
|---|---|---|
| Successful generation | — | 200 |
| Missing/non-string/empty input | `EMPTY_INPUT` / `INVALID_REQUEST` | 400 |
| Input over 10,000 characters | `INVALID_REQUEST` | 400 |
| Mode not `quiz`/`flashcards` | `INVALID_REQUEST` | 400 |
| Gemini call exceeds timeout (after 1 retry) | `AI_TIMEOUT` | 408 |
| Gemini rate limit | `AI_RATE_LIMITED` | 429 |
| Gemini unreachable / other provider failure | `AI_REQUEST_FAILED` | 502 |
| Gemini returned unparseable/invalid-shape JSON | `INVALID_AI_RESPONSE` | 502 |
| Anything else unexpected | `INTERNAL_ERROR` | 500 |

The frontend never needs to understand Gemini-specific internals — it only ever sees `success` or a typed `error`.

## Validation pipeline

AI output is never trusted as-is. It passes through two independent layers on the backend, then is re-validated on the frontend before touching React state:

1. **Schema validation (Zod)** — asks "does the data have the right shape?" (exactly 4 options per question, 5–10 questions/cards, correct `correct_answer` range, non-empty strings, etc.)
2. **Logical validation** — asks "is this shape actually usable?" (no duplicate questions, no duplicate options within a question, `correct_answer` must point at a real option).

Only content that passes both is returned to the client, and the client re-runs the same checks before rendering.

## Frontend state model

```
idle    → input screen
loading → LoadingState
success → ResultView (Quiz or Flashcards)
error   → ErrorState + Retry
```

No untracked booleans — one `status` value drives the entire UI deterministically.

## Stale-response protection

Every call to `generate()` gets an incrementing `requestId`. Before applying a response to state, the hook checks that the request is still the most recent one; if not, the result is silently discarded. An `AbortController` also cancels the previous in-flight request whenever a new one starts, so a user firing off multiple requests in quick succession only ever sees the result of the last one.

## What we deliberately did not build

To keep a clean, fully-working core rather than several half-finished features: no authentication, no database, no RAG/vector store, no LangChain/LangGraph, no chat interface, no multi-provider LLM support, no file upload, no user accounts, no agent framework.

## A note on the Gemini model migration

Mid-project, `gemini-2.5-flash` stopped being available to new API keys/projects — new keys hit a `404` with a message directing callers to `gemini-3.8-flash`. This surfaced as an `AI_RATE_LIMITED`/`404`-type failure during testing and was diagnosed by:

1. Confirming the running server had actually picked up a new API key (it hadn't — `nodemon` doesn't watch `.env` by default, so a restart was required).
2. Testing the key directly against the Gemini SDK in isolation, outside the app, which surfaced Google's own deprecation message.
3. Updating `model: "gemini-2.5-flash"` → `model: "gemini-3.8-flash"` in `services/gemini.js`. The existing `generateContent` call pattern is unaffected — Google's newer `Interactions API` is now recommended for new projects, but `generateContent` remains fully supported, so no other code changed.

This is left documented here deliberately, since it's a real example of handling an external dependency changing under the project mid-build.

## Testing / failure cases

Verified manually against the running server:

| Case | Input | Result |
|---|---|---|
| Empty input | `{"input":"","mode":"quiz"}` | `400 EMPTY_INPUT` ✅ |
| Invalid mode | `{"input":"Binary Search","mode":"invalid"}` | `400 INVALID_REQUEST` ✅ |
| Valid quiz request | `{"input":"Binary Search","mode":"quiz"}` | `200`, valid quiz JSON ✅ |
| Valid flashcards request | `{"input":"Operating Systems","mode":"flashcards"}` | `200`, valid flashcards JSON ✅ |
| Gemini rate-limited | (real 429 from provider) | `429 AI_RATE_LIMITED`, not retried ✅ |
| Backend down | frontend generate with server stopped | `ErrorState` + retry shown ✅ |
| Rapid double-generate | two `generate()` calls in quick succession | only the latest result rendered, no flicker of the stale one ✅ |
| Simulated timeout | temporarily lowered timeout threshold | retried once, then `408 AI_TIMEOUT` ✅ |
| Malformed AI JSON | simulated invalid `response.text` | `502 INVALID_AI_RESPONSE` ✅ |

## Deployment

Both frontend and backend are deployed, since the Gemini API key must stay server-side.

- **Frontend (Vercel):** [https://study-assistant-liard-two.vercel.app](https://study-assistant-liard-two.vercel.app)
- **Backend (Render):** https://study-assistant-api-vv5u.onrender.com

The frontend calls the backend via `VITE_API_BASE_URL`, and the backend restricts CORS to the deployed frontend origin via `CLIENT_ORIGIN`. `GEMINI_API_KEY` is set only on the backend and is never exposed to the client.

> Note: the backend runs on Render's free tier, which spins down after periods of inactivity. The first request after idle time may take 20–30 seconds while the instance wakes up.

## AI tool usage

AI tools were used throughout this project, primarily for planning and problem-solving rather than generating the application unreviewed.

- **Architecture & rubric alignment (Chatgpt):** used to design the end-to-end pipeline (React → Express → Gemini → Zod validation → logical validation → UI), map each decision against the evaluation rubric, and settle on the state model (`idle` / `loading` / `success` / `error`), the discriminated-union data model for quiz vs. flashcards, and the stale-response/AbortController protection.
- **Debugging & code review (Claude):** used to review `server.js` before deployment, which caught a hardcoded port, a hardcoded CORS origin that would break in production, and a debug log that printed part of the API key. Also used to diagnose live deployment issues (a transient Gemini `AI_REQUEST_FAILED` after a cold start, and an `AI_RATE_LIMITED` response from hitting the free-tier Gemini quota during testing) by tracing them to the exact error-handling branch in the code.
- **Deployment (Claude):** used for step-by-step guidance deploying the frontend to Vercel and the backend to Render, including correctly separating the frontend-only `VITE_API_BASE_URL` variable from the backend-only `GEMINI_API_KEY`, so the API key is never exposed to the browser.

All AI-suggested code was read, tested, and understood before being committed — nothing was merged without knowing what it does and why. The core engineering decisions (schema design, validation strategy, error taxonomy, state model) were made deliberately and can be explained and modified live, which is reflected in the [architecture](#architecture) and [validation pipeline](#validation-pipeline) sections above.
